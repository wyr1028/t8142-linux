# "proxy 读出来全是 0" —— 一条被误诊的卡点

**2026-10-11 分析(纯读源码,不需要 M5)**

---

## 第三方怎么说

> `proxyclient/hw/` 里硬编码的是 M1/M2 时代的 MMIO 基址,M5 上这些地址挪了,
> 所以 `read32` 全返回 0。

**这条被当成了"没人做成的两件事"之一。**

## 实际源码说什么

```python
# proxyclient/m1n1/hw/pmgr.py
class PMGR:
    def __init__(self, u):
        self.node = u.adt["/arm-io/pmgr"]           # ← 从运行时 ADT 查
        self.regs = [
            PMGRRegs0(u, self.node.get_reg(0)[0]),   # ← 地址来自 ADT 的 reg
            PMGRRegs1(u, self.node.get_reg(1)[0]),
            PMGRRegs2(u, self.node.get_reg(2)[0]),
        ]

# proxyclient/m1n1/hw/i2c.py
class I2C:
    def __init__(self, u, adt_path):                 # ← 传 ADT 路径
```

**全 `proxyclient/m1n1/hw/` 目录 grep 不到硬编码的物理地址。**

**结论:地址是运行时从 m1n1 上报的 ADT 里取的,不是硬编码。**
**"硬编码 M1/M2 地址"这条说法不成立。**

---

## 那真正的原因可能是什么

### 假设:窗口偏移被当成 M1 的了

已经核实的事实(`docs/HOW-TO-UNDO.md` 同批):

| | 子地址 → 物理地址的窗口 |
|---|---|
| M1 | `bus 0x0 -> phys **0x2_0000_0000**` |
| **M5** | `bus 0x0 -> phys **0x2_1000_0000**` |

**差 `0x1000_0000`(256 MB)。**

如果链路里任何一处:

- 假设了 M1 的窗口
- 或者拿了 ADT 的**子地址**当物理地址直接用(m1n1 的 C 侧、或 `adt_get_reg` 的调用方)

那么对 M5 就会读到**未映射区域** —— **读未映射地址通常返回 0,而不是报错。**

**这和症状完全吻合。**

---

## 怎么验(等真机)

**不需要先改任何代码的检查顺序:**

1. 抓 m1n1 启动日志(`picocom`),里面会打印它认到的地址表
2. 拿 M5 的**已知物理地址**去读。例如 UART0:
   ```
   子地址   0x1_95200000
   物理     0x3_a5200000      ← ADT 的 ranges 翻译后
   ```
   - 读物理地址返回非零 → 窗口那层有问题
   - 读子地址返回非零 → 反而是另一回事
3. 一个个试,能把"差在哪一层"钉死

**参考地址**:[M5-MEMMAP.md](M5-MEMMAP.md)(146 条,已交叉验证)
